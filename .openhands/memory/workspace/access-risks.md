# Доступ клиента: почта или аккаунт, и что он сможет делать

## 1. Почта или аккаунт?

**Можно пригласить по почте.** GitHub это разрешает: в поле поиска вводишь не логин, а адрес почты клиента.

Но есть три важных оговорки.

**Аккаунт всё равно понадобится.** Без аккаунта на GitHub доступ получить нельзя. Если пригласить по почте человека без аккаунта, GitHub предложит ему зарегистрироваться. Пока не зарегистрируется — доступа нет.

**Приглашение по почте живёт 7 дней.** Потом сгорает, и надо отправлять заново. Приглашение по логину так не сгорает.

**Почта должна быть та, что привязана к аккаунту.** Если человек зарегистрирован на одну почту, а ты пригласил на другую, он приглашение не увидит.

**Вывод: проси логин, а не почту.** Логин надёжнее, не сгорает и исключает ошибку с чужой почтой. Почта — запасной вариант, если клиент не может найти свой логин.

Если клиент вообще не хочет регистрироваться — способ 2 не подходит. Тогда либо способ 1 (передача репозитория, тоже нужен аккаунт), либо ты просто держишь сайт у себя и правишь сам за доплату.

## 2. Что клиент сможет делать

Это главное, что нужно понять до того, как давать доступ.

### Сможет

- Менять любые файлы сайта
- Удалять файлы, в том числе всю папку с картинками
- Добавлять свои файлы и страницы
- Публиковать что угодно на твоём адресе
- Сломать сайт так, что он перестанет открываться
- Смотреть всю историю правок

**Проще говоря: с правом Write клиент может делать с сайтом что угодно. Включая полное удаление.**

### Не сможет

- Забрать репозиторий себе
- Удалить репозиторий целиком
- Добавить или убрать других людей
- Менять настройки и адрес сайта
- Сменить видимость репозитория
- Увидеть твои секретные ключи

Про ключи я проверил отдельно: в репозитории их нет. Файл `.env.example` — это пустой шаблон, и в проекте есть даже проверка на случайные секреты. Пароли и ключи лежат отдельно, на сервере, и в репозиторий не попадают. Это хорошо.

## 3. Главная проблема — ты собираешься дать доступ к СВОЕМУ проекту

Вот это самое важное.

Репозиторий `deeprealm-site` — это не пустой склад. Внутри:

- Сайт сообщества Deeprealm
- Игра «Пожиратель Пустоты»
- Твой сервер, бот и ИИ-помощники
- 97 файлов, из них 48 — в папке docs

Ты собираешься показать клиенту витрину, а дать доступ к своему рабочему проекту. Если клиент окажется неаккуратным или недобросовестным, он сломает витрину, которую ты показываешь другим. Игру, сайт сообщества, всё.

**Так делать не надо.** Это как отдать ключ от мастерской заказчику, который просил подержать рамку.

## 4. Как правильно

**Заводи отдельный репозиторий под каждого клиента.**

Один клиент — один репозиторий. Например `sait-dlya-ivana` или `cafe-romashka`. Туда кладёшь только его сайт, и ему даёшь доступ туда.

Что это даёт:

- Твой проект остаётся закрытым и целым
- Клиент видит только своё, а не все твои работы
- Если он что-то сломает — пострадает только его сайт
- Легко передать ему репозиторий целиком, когда попросит
- Легко удалить, если заказ отменили

**Как создать:**

1. На github.com нажми зелёную кнопку **New** — создать новый репозиторий
2. Название — по клиенту или проекту
3. Выбери **Public** (иначе сайт не будет работать бесплатно)
4. Галочку «Add a README file» можно поставить
5. Создай
6. Потом в настройках: **Settings → Pages**, включи публикацию из ветки main, папка `/docs`
7. Скинь туда файлы сайта
8. И только теперь давай клиенту доступ — в этот репозиторий, а не в свой

Для мелкого сайта это занимает пять минут, а проблему решает полностью.

## 5. Ещё одна опасность, о которой мало кто думает

Отдавая доступ, ты отдаёшь **адрес**. Клиент сможет опубликовать на нём что угодно — например, чужую рекламу или мошенническую страницу.

Если на такую страницу будут жаловаться, достанется твоему аккаунту. А если это твой основной аккаунт — можно потерять всё.

Поэтому:

- Не давай доступ к основному аккаунту посторонним
- Отдельный репозиторий под каждого клиента обязателен
- Если заказ закончился, а клиент пропал — забери доступ, не жди

## 6. Что сказать клиенту

> Доступ дам на отдельный репозиторий, он только ваш. Там будет лежать ваш сайт, ничего лишнего.
>
> Пришлю приглашение на GitHub — нажмите Accept, иначе доступ не включится.
>
> Вы сможете менять тексты, картинки и страницы. Настройки и адрес остаются у меня, так надёжнее: случайно сломать что-то важное не получится.
>
> Когда захотите забрать сайт полностью — оформим передачу репозитория на ваш аккаунт.

Честно, понятно и без лишних слов.

## Коротко

- Приглашать лучше по **логину**, почта — запасной вариант, и она сгорает за 7 дней
- Аккаунт на GitHub нужен в любом случае
- С правом Write клиент может делать с сайтом **что угодно**, включая удаление
- Не сможет: забрать репозиторий, менять настройки, увидеть ключи
- **Не давай доступ к своему проекту** — заводи отдельный репозиторий под клиента
