## Проверка дневника «Волна» без ручного ввода пароля

- Сценарий с паролем гоняется автоматически: `preview-src/verify_all.js <origin>`, драйвер `preview-src/cdp_run.js`, конверт считает `preview-src/make_envelope.js` (Node WebCrypto, PBKDF2 250000 + AES-GCM — тот же формат, что в `crypto.js`).
- `--virtual-time-budget` не годится: он прокручивает таймеры, но не ждёт реального счёта PBKDF2. Нужен CDP с `awaitPromise: true`.
- `pwa.js` в тестовой копии отключать: сервис-воркер перезагружает страницу при первой установке и рвёт замер.
- Разным портам — разный `localStorage`. Для сценария «чистый браузер» поднимать новый порт, иначе состояние протечёт из прошлого прогона.

## Вёрстка: проверяем измерениями, а не на глаз

- В контейнере есть `chromium`. Снимок + `--dump-dom` с пробным `<script>`, который печатает `getComputedStyle` и `getBoundingClientRect` в `<pre>` с маркерами `\x01`/`\x02` — так меряем реальную геометрию.
- `document.fonts.ready` перед замерами: иначе ширины считаются по подставному шрифту.
- Ширина `Space` в Mulish 16px = 4,22px, в system-ui = 5,09px. Тесно, поэтому в `body` стоит `word-spacing: .1em`.
- Частая ловушка: правило `@media (max-width: 560px) .card { padding: 20px }` перебивает `.paper`, у которого тот же вес. Лечится повышением точности селектора (`.notebook .paper`) и расчётом отступа от линии: `calc(var(--line-x) + var(--line-gap))`.
- Контраст красной линии на `#FFFCF6` при `rgba(255,122,122,.45)` был 1,49 — ниже порога 3:1. Взял `#D95656` (3,79) и `rgba(255,138,146,.9)` (6,24).
- `sw.js` у «Волны» — network-first, поэтому правки CSS доходят сразу; кэш только для офлайна.
- Размеры окон в headless: `--window-size=390` даёт viewport 500px (минимум chromium). Для узких экранов брать 360.
- Браузерные проверки кэшируют `style.css`: перед прогоном включать `Network.setCacheDisabled`, иначе проверка ругается на старые стили, которых в файле уже нет.
- Буфер обмена в headless доступен только активной вкладке: нужны `Page.bringToFront` и разрешения `clipboardReadWrite`, иначе и запись, и чтение падают с `NotAllowedError`.
- Меню шапки узкое на планшете: при 768–860px оно не помещается и даёт горизонтальную прокрутку, если добавлять пункты в `.nav`. Проверять `check_workshop_layout.js` после каждого нового пункта.

## Сайт из чужой песочницы засыпает

Песочница чужой беседы со временем уходит в `PAUSED`, и сайт отдаёт 404.
Это не поломка кода — её нужно разбудить и поднять сервер заново:

1. `GET /api/v1/sandboxes/search?limit=50` (Bearer `$OPENHANDS_API_KEY`) — найти
   свою песочницу по id и посмотреть `status`.
2. `POST /api/v1/sandboxes/{id}/resume` — поднять. Ждать статус `RUNNING`
   (обычно 20–30 секунд).
3. **Ключ сессии меняется** после resume: взять свежий `session_api_key` из
   ответа `sandboxes/search`, старый даст `{"detail":"Unauthorized"}`.
4. Пакеты сбрасываются: `pip install -r requirements.txt` (Flask, Markdown, nh3).
5. `setsid nohup python3 run.py > server.log 2>&1 < /dev/null &`, затем проверить
   порт 12000 и сайт снаружи.

База в `instance/` переживает паузу — данные остаются на месте.
Держать актуальный ключ в `preview-src/.logos-session-key`.

## Хостинг сайтов на GitHub Pages

Песочница со временем засыпает и сайт отдаёт 404. Постоянный хостинг для
заказных сайтов — GitHub Pages: адрес не зависит от песочницы.

- **Logos (готово):** https://grigoriy131112-sketch.github.io/logos/
- **Volna:** https://grigoriy131112-sketch.github.io/volna/

Как это устроено у «Логоса» (репозиторий `logos`):

- Pages — это статика, Flask-сервер на ней не живёт. Поэтому в репозитории
  есть сборка: `tools/build_static.py` рендерит страницы самим приложением
  (вид совпадает с живым сайтом) в папку `docs/`, контент берётся из
  `data/content.json`.
- `.github/workflows/pages.yml` при пуше в `main` прогоняет `test_app.py`,
  пересобирает сайт и обновляет ветку `gh-pages` — оттуда Pages и отдаёт
  файлы. После правки `data/content.json` достаточно запушить `main`.
- **Токен интеграции не управляет Pages через API** (`Resource not accessible
  by integration`) — ни создать сайт, ни сменить источник. Но Pages
  включается сам, когда появляется ветка `gh-pages`. Поэтому публикация
  идёт через ветку, а не через `actions/deploy-pages`.
- Сайт живёт в подкаталоге `/logos/`, поэтому сборка задаёт
  `SCRIPT_NAME=/logos`, а абсолютные адреса (RSS, sitemap, robots) строятся
  через `url_for(..., _external=True)`. Склейка с `request.url_root` даёт
  двойной префикс.
- Формы, которым нужен сервер (публикация, отклики, реакции), в статике
  заменяются пояснениями; поиск и «Случайная мысль» работают в браузере
  (`app/static/js/static.js`).

Проверка статики в браузере: `node preview-src/check_logos_static.js <адрес>`
— 30 сценариев, все должны пройти.

### Отклики (комментарии) через Giscus

GitHub Pages не умеет принимать комментарии: чтобы отклик увидели все,
нужен сервер. Решение — Giscus: обсуждения хранятся в GitHub Discussions
репозитория `logos`, а на страницу публикации вставляется окно Giscus.

- **Нужен ручной шаг:** Discussions включаются только в интерфейсе GitHub
  (Settings → Features → Discussions). Токен интеграции этого не может —
  и GraphQL `updateRepository`, и REST `PATCH /repos` отвечают 403
  `Resource not accessible by integration`.
- После включения на странице https://github.com/apps/giscus поставить
  приложение на репозиторий, затем на https://giscus.app получить
  `data-category-id` для категории «Отклики». Тип категории — Announcements
  (так рекомендует Giscus: тогда обсуждения создаёт только Giscus и
  владелец, а не случайные посетители); название можно задать своё.
- Идентификаторы лежат в `GISCUS` (`app/__init__.py`), `repo_id` уже есть
  (`R_kgDOU4kzsQ`). Пока `category_id` пуст, блок не выводится вовсе —
  иначе Giscus показал бы свою ошибку. Форма отклика при этом работает
  по-старому, а в статике вместо неё пояснение.
- CSP в `app/__init__.py` разрешает `https://giscus.app` в `script-src` и
  `frame-src`. Без `frame-src` окно обсуждения не загрузилось бы: `default-src
  'self'` его блокирует.
- Тему окна синхронизирует `app/static/js/giscus.js`: при смене темы сайта
  он шлёт окну `postMessage({giscus:{setConfig:{theme}}})`. Просто поменять
  `data-theme` у тега скрипта нельзя — Giscus убирает свой тег из DOM после
  загрузки, и атрибут уже ни на что не влияет.
- Обсуждение привязано к публикации через `data-term="logos-post-<id>"` и
  `mapping="specific"` — так одна запись не смешивается с другой.
- Окно грузится лениво (`loading: "lazy"`): пока страница не прокручена к
  откликам, фрейма в DOM нет. Проверять отклики нужно с прокруткой, иначе
  проверка «врёт»: контейнер есть, а окна ещё нет.
- Окно Giscus — отдельный процесс (cross-origin): в дереве фреймов страницы
  его не видно, искать надо среди целей браузера (`/json/list`, `type=iframe`).

Живая проверка откликов: `node preview-src/check_logos_giscus.js <адрес>`
(окно отвечает 200, CSP не нарушен) и
`node preview-src/check_logos_giscus_theme.js <адрес>` (тема следует за сайтом).

## Мастерская «Логоса» (запись без сервера)

На GitHub Pages нет сервера, поэтому «писать» на сайте было нечем. Решение —
мастерская `/workshop`: профиль и свои мысли живут в `localStorage` браузера.

- Псевдоним без регистрации: ничего не уходит на сервер, профиль принадлежит
  браузеру. Есть «Сохранить копию»/«Загрузить копию» — выгрузка мыслей в
  файл, чтобы они пережили очистку данных браузера.
- Правка и удаление есть и у мыслей в мастерской, и у публикаций в блоге
  (`/post/<id>/edit`, `/post/<id>/delete`).
- Свой текст экранируется до разметки: тег или скрипт в записи показывается
  как текст. Это проверяется сценарием в браузерной проверке.
- В полной версии (Flask) есть кнопка «Опубликовать в ленте»; сборка скрывает
  её, выставляя `data-can-publish="false"`.

Проверки мастерской: `node preview-src/check_logos_workshop.js <адрес>` —
27 сценариев (профиль, запись, Markdown, правка, удаление, сохранность после
перезагрузки, XSS). Вёрстка: `node preview-src/check_workshop_layout.js`.
